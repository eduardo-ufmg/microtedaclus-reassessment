\chapter{Methodology Reassessment}
\label{chap:methodology_reassessment}

The \textit{Evolving clustering algorithm based on mixture of typicalities for stream data mining} paper presents promising results for the microTEDAclus model \cite{maia2020evolvclus}. Before conclusions can be drawn from those results, however, it is important to assess the methodology used in the original work. In this chapter, only its methodology is reviewed, since the following paper, \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile} assumes its validity and does not perform further investigation on it.

The next sections examine weaknesses from the evaluated model implementation to the experiments protocol, including the evaluation metrics and procedures. The goal of this reassessment is to identify potential issues in the original work's methodology that could affect the validity of its results and conclusions. By doing so, a more rigorous and accurate evaluation of the microTEDAclus model can be conducted, leading to more reliable conclusions about its performance and applicability in real-world scenarios.

\section{Model Implementation} \label{sec:model_implementation}

In the fifth section of the original work, \textbf{Methodology and experiments}, \cite{maia2020evolvclus} provides a URL to the public GitHub repository where the code for the experiments can be found: \url{https://github.com/cseveriano/evolving_clustering}. To ensure persistence of the code, a fork of the original repository was created at the commit \texttt{50dd2b4}, which is the last commit to the repository at the time of this reassessment \cite{eduardo2026evolvingclustering}. The implementation of the microTEDAclus model is found in the \texttt{src/models/evolving/EvolvingClustering.py} file of the repository.

It is important to note that the implementation of the microTEDAclus model found in the public repository is not the same as the one described in the original work, but is the one that, when submitted to the repository experiments, produced the results shown in the original work. A closer inspection of the code reveals that said implementation have characteristics that are similar to the ones described in the updated version of microTEDAclus, which is presented in the PHD thesis \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile}. Furthermore, it handles the outlier-condition logic's problem stated in \cref{sss:incorrect_condition_logic}, but introduces mathematical errors in the implementation of expressions \cref{eq:recursive_eccentricity} and \cref{eq:normalized_typicality}, which are the core of the microTEDAclus model. This is a problem because the results of the experiments are not comparable to the ones presented in the original work, and the conclusions drawn from those results may not be valid.

The most notable and critical change from the paper's formulation to the implementation is the introduction of an explicit decayment logic, specifically the one described in \cite{galindo2021lastmile}. The model constructor's signature is seen in \cref{snippet:maia_implementation_constructor}.

\begin{lstlisting}[float, language=Python, caption={Constructor of the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_constructor}]
def __init__(self, macro_cluster_update=1,
                verbose=0, variance_limit=0.001, decay = 100, debug=False, plot_graph=False):
    self.verbose = verbose
    self.total_num_samples = 0
    self.micro_clusters = []
    self.macro_clusters = []
    self.active_macro_clusters = []
    self.graph = nx.Graph()
    self.active_graph = nx.Graph()
    self.variance_limit = variance_limit
    self.macro_cluster_update = macro_cluster_update
    self.debug = debug
    self.plot_graph = plot_graph
    self.changed_micro_clusters = []
    self.fading_factor = 1 / decay
\end{lstlisting}

The introduced factor, $\text{fading\_factor} = \frac{1}{\text{decay}}$, corresponds to the $\rho$ parameter of the decayment logic described in \cite{galindo2021lastmile}, which is a value between 0 and 1 that determines the rate at which the model forgets old data. It is used in two distinct methods of the implementation. In \cref{snippet:maia_implementation_prune_microclusters}, it linearly decays the \texttt{life} of the microclusters that were considered 'not active' in the current \texttt{fit} iteration. Such functionality loosely corresponds to the one described in \cite{galindo2021lastmile}, but does not match it exactly; the paper states that the decayment is applied to the microclusters that are not updated by the sample being processed, while the "activeness" of a microcluster is determined in the macrocluster construction phase, and depends only on the comparison between the microcluster's and the macrocluster's densities.

\begin{lstlisting}[float, language=Python, caption={Pruning of microclusters in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_prune_microclusters}]
def prune_micro_clusters(self):
    for mc in self.micro_clusters:

        if not mc["active"]:
            mc["life"] = mc["life"] - self.fading_factor

            if mc["life"] < 0:
                self.micro_clusters.remove(mc)

                if mc in self.changed_micro_clusters:
                    self.changed_micro_clusters.remove(mc)

                self.graph.remove_node(mc["id"])
\end{lstlisting}

The second method where the fading factor is used is \cref{snippet:maia_implementation_update_life}. In this method, the fading factor acts as a scaling coefficient for a dynamic reward or penalty. It evaluates the Euclidean distance of the new sample to the micro-cluster's center relative to its standard deviation. If the sample is closer than the standard deviation, \texttt{life} increases, otherwise it decreases. The fading factor scales the amount of increase or decrease, which means that the model will forget old data faster if the fading factor is higher.

\begin{lstlisting}[float, language=Python, caption={Update of microclusters' life in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_update_life}]
    def update_life(self, xk, micro_cluster):
        previous_mean = micro_cluster["mean"]
        previous_var = micro_cluster["variance"]
        if previous_var > 0:
            d = EvolvingClustering.get_euclidean_distance(xk, previous_mean)
            dist = np.sqrt(np.sum(d))
            rt = np.sqrt(previous_var)
            micro_cluster["life"] = micro_cluster["life"] + (((rt - dist) / rt) * self.fading_factor)
        else:
            micro_cluster["life"] = 1
\end{lstlisting}

Such decayment logic is not present neither in the original work nor in the updated version of microTEDAclus, and its introduction in the implementation found in the public repository is not justified or explained in any of those works. This is a problem because it introduces a significant change to the model's behavior that is not accounted for in the original work, and it may affect the results of the experiments and the conclusions drawn from them.

Another significant change from the paper's formulation to the implementation is the handling of microcluster activation. \cref{info:microcluster_activation_criterion} and \cref{critique:use_of_unstable_density} present the criterion and use for microcluster activation stated in the original work. The implementation's procedure deviates from it and is described in \cref{alg:microcluster_activation_criterion_pseudocode}. Note that this pseudocode corresponds to the current work's interpretation of the code provided in the public repository, and it is not acknowledged or explained in neither the original work or the updated version of microTEDAclus' presentation.

\begin{algorithm}[htbp]
\caption{Microcluster activation criterion used in the implementation found in the public repository}
\label{alg:microcluster_activation_criterion_pseudocode}
\begin{algorithmic}[1]
\Require $m_i$, $i = 1, 2, \dots, n$ (the set of all microclusters)
\Ensure $\mathcal{M}_j, j = 1, 2, \dots, m$ (the set of macroclusters)
\State Construct the graph $\mathbb{G}_0$ by connecting microclusters that satisfy the intersection condition described in \cref{eq:microcluster_intersection_condition}
\State Build a macrocluster $\mathcal{M}_j$ for each connected component of $\mathbb{G}_0$
\For{each macrocluster $\mathcal{M}_j$}
    \State Compute its microclusters' activation according to \cref{critique:use_of_unstable_density}
\EndFor
\State Capture the active graph $\mathbb{G}_1$ by removing the non-active microclusters from $\mathbb{G}_0$
\State Build a macrocluster $\mathcal{M}_j$ for each connected component of $\mathbb{G}_1$
\end{algorithmic}
\end{algorithm}

Hence, it can be inferred that, because $\mathbb{G}_0$ is subject to the ill condition of microcluster collapse, predicted by the original work, a second graph-building pass is performed over the microclusters considered to be active according to \cref{critique:use_of_unstable_density}. The resulting graph, $\mathbb{G}_1$, is expected to be secured from the overlap condition. The macroclusters built from it are the output of the macrocluster construction phase. Not only this change deviates from the original work's formulation, but it also introduces a significant increase in the computational complexity of the macrocluster construction phase, which may affect the results of the experiments and the conclusions drawn from them.

The process is performed by \cref{snippet:maia_implementation_update_macroclusters}, which calls \cref{snippet:maia_implementation_define_macroclusters} to build the macroclusters from the graph $\mathbb{G}_0$ followed by \cref{snippet:maia_implementation_define_activations} to determine the active microclusters, capture the active graph $\mathbb{G}_1$, and extract the final macroclusters from it.

\begin{lstlisting}[float, language=Python, caption={Update of macroclusters in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_update_macroclusters}]
def update_macro_clusters(self):
    self.define_macro_clusters()
    self.define_activations()
\end{lstlisting}

\begin{lstlisting}[float, language=Python, caption={Definition of macroclusters from the graph $\mathbb{G}_0$ in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_define_macroclusters}]
def define_macro_clusters(self):
    for mi in self.changed_micro_clusters:
        for mj in self.micro_clusters:
            if mi["id"] != mj["id"]:
                edge = (mi["id"],mj["id"])
                if EvolvingClustering.has_intersection(mi, mj):
                    self.graph.add_edge(*edge)
                elif EvolvingClustering.nodes_connected(mi["id"],mj["id"], self.graph):
                    self.graph.remove_edge(*edge)

    self.macro_clusters = list(nx.connected_components(self.graph))
    self.changed_micro_clusters.clear()
\end{lstlisting}

\begin{lstlisting}[float, language=Python, caption={Definition of active microclusters and macroclusters from the graph $\mathbb{G}_1$ in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_define_activations}]
def define_activations(self):
    self.active_graph = self.graph.copy()
    for mg in self.macro_clusters:
        num_micro = len(mg)
        total_density = 0
        for i in mg:
            dens = next(item["density"] for item in self.micro_clusters if item["id"] == i)
            total_density += dens
        mean_density = total_density / num_micro
        for i in mg:
            mi = next(item for item in self.micro_clusters if item["id"] == i)
            mi["active"] = (mi["num_samples"] > 2) and (mi["density"] >= mean_density)
            if not mi["active"]:
                self.active_graph.remove_node(mi["id"])
    self.active_macro_clusters = list(nx.connected_components(self.active_graph))
\end{lstlisting}

\cref{snippet:maia_implementation_is_outlier} implements \cref{eq:outlier_condition} and substitutes \cref{critique:incorrect_condition_logic} by \cref{eq:corrected_condition_logic_for_outliers}.

\begin{lstlisting}[float, language=Python, caption={Outlier detection in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_is_outlier}]
def is_outlier(self, s_ik, var_ik, norm_ecc):
    if s_ik < 3:
        outlier = (var_ik > self.variance_limit)
    else:
        mik_sik = 3 / (1 + math.exp(-0.007 * (s_ik - 100)))
        outlier_limit = ((mik_sik ** 2) + 1) / (2 * s_ik)
        outlier = (norm_ecc > outlier_limit)
    return outlier
\end{lstlisting}

Finally, \cref{eq:recursive_eccentricity} and \cref{eq:normalized_typicality} are implemented as \cref{snippet:maia_implementation_get_eccentricity} and the previous to last expression of \cref{snippet:maia_implementation_calculate_membership}, respectively.

\begin{lstlisting}[float, language=Python, caption={Eccentricity calculation in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_get_eccentricity}]
def get_eccentricity(x, num_samples, mean, var):
    if var == 0 and num_samples > 1:
        result = (1/num_samples)
    else:
        a = mean - x
        result = ((1 / num_samples) + ((np.linalg.norm(a) * 2 / len(a)) ** 2 / (num_samples * var)))

    return result
\end{lstlisting}

The mathematical expansion of the main expression in \cref{snippet:maia_implementation_get_eccentricity} is \cref{eq:maia_implementation_eccentricity_eq}, which is fundamentally different from \cref{eq:recursive_eccentricity}.

\begin{equation}
    \xi^i\left(x\right) = \frac{1}{S^i_k} + \frac{4\lVert\mu^i_k - x\rVert^2}{d^2S^i_k\left(\sigma^i_k\right)^2}
    \label{eq:maia_implementation_eccentricity_eq}
\end{equation}

\begin{lstlisting}[float, language=Python, caption={Membership calculation in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_calculate_membership}]
def calculate_membership(x, active_micro_clusters):
    total_density = 0
    for m in active_micro_clusters:
        total_density += m["density"]

    mb = 0
    for m in active_micro_clusters:
        d = m["density"]

        t = 1 - EvolvingClustering.get_normalized_eccentricity(x, m["num_samples"], m["mean"], m["variance"])
        mb += (d / total_density) * t
    return mb
\end{lstlisting}

The expression for the intermediary typicality calculation in \cref{snippet:maia_implementation_calculate_membership} cannot be mathematically rewritten to match \cref{eq:normalized_typicality}, and is not equivalent to it.

The updated implementation of microTEDAclus, which is presented in the PHD thesis \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile}, was provided by the work's author, but is not publicly available. Its main improvements from the original implementation are the introduction of partial support to the use of the cossine distance as distance metric, the refactor of the decayment logic, and the extraction of the microcluster structure to a separate class.

\section{Benchmark Models}

\subsection{Benchmark Models Implementation Used in the Original Work}

In it's experiments, the original work compares the proposed microTEDAclus model against three benchmark models: DenStream \cite{cao2006density}, CluStream \cite{aggarwal2003framework}, and StreamKM++ \cite{ackermann2012streamkmpp}, commonly used in the literature for data stream clustering evaluation \cite{hyde2017fully,akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline} as benchmark models. The validity of the experiments, however, depends on the implementation and execution of those models. As stated in the article and verified in the public repository, the implementations of those models are sourced from the \texttt{R} package \texttt{streamMOA} through the binding provided by \texttt{rpy2}.

However, because \texttt{streamMOA} is a wrapper for the Java-based MOA framework \cite{streamMOA2024}, two layers of interface overhead are introduced in the execution of the benchmark models. Such overhead is expected to have a significant impact on both the execution time and the memory footprint perceived by the \texttt{Python} experiment orchestrator. To verify such hypothesis, a benchmarking experiment was conducted as described in \cref{alg:benchmarking_experiment}.

\begin{algorithm}[htbp]
\caption{Benchmarking experiment to evaluate the impact of interface overhead on the execution time and memory footprint of the benchmark models}
\label{alg:benchmarking_experiment}
\begin{algorithmic}[1]
\Require $M$ the set of benchmark models, $n = 100000$ the number of samples to be processed, $d = 10$ the dimensionality of the samples, $C = 5$ the number of classes, $c = 50$ the number of clusters, $r = 8$ the number of runs
\Ensure $T$ the execution time and $F$ the memory footprint of each model
\State $S \gets \texttt{generate\_dataset\_with\_riverRandomRBF}(n, d, C, c)$
\For{each model $m \in M$}
    \State $T_m \gets []$
    \State $F_m \gets []$
    \For{$i = 1$ to $r$}
        \State $t, f \gets \texttt{run\_model\_with\_time\_and\_memory\_measurement}(m, S)$
        \State $T_m.\texttt{append}(t)$
        \State $F_m.\texttt{append}(f)$
    \EndFor
    \State $T[m] \gets \texttt{compute\_statistics}(T_m)$
    \State $F[m] \gets \texttt{compute\_statistics}(F_m)$
\EndFor
\end{algorithmic}
\end{algorithm}

\subsection{TEDACloud and CEDAS}

It is not clear why, even though the original work references TEDACloud \cite{bezerra2016tedacloud} and CEDAS \cite{hyde2017fully}, it does not include them in the experiments. CEDAS's introductory paper points to its official \texttt{MATLAB} implementation in \url{https://rhyde67.github.io/CEDAS/}, which was easily ported to \texttt{Python} and is available in the public repository of this reassessment. TEDACloud's introductory paper does not provide a public implementation, but a \texttt{Python} implementation was derived from the algorithm description in the paper and is also available in this work's public repository. Both implementations are included in this reassessment's experiments.

\subsection{AutoCloud}

AutoCloud's introductory paper \cite{bezerra2020autocloud} was published approximately at the same time as the microTEDAclus paper, thus it is not expected to have been included in the original work's experiments. The algorithm is presented as an improvement over TEDACloud, and since it is a recent and relevant work, it is included in this reassessment's experiments. A \texttt{Python} implementation was derived from the algorithm description in the paper and is available in this work's public repository.

\subsection{Hyperparameter Tuning} \label{subsec:hyperparameter_tuning}

All the models evaluated in this reassessment have hyperparameters that can be tuned to improve their performance, even those for which the introductory paper chooses to use default values. To ensure that any model is not unfairly disadvantaged by the choice of hyperparameters, all the following experiments are preceded by a hyperparameter tuning phase in which the first 20\% of the samples of each stream is extracted to perform a Bayesian optimization \cite{ozaki2025optunahub} search for the best hyperparameters of each model. Such an approach prevents data leakage \cite{kaufman2012leakage,kapoor2023leakage} because the evaluation phase is performed on the unseen remaining 80\% of the samples of the stream. Furthermore, it is basically an automated and safer approach than the one taken by the experiments in the original work, in which the parameters that maximize the score over the entire dataset are selected for the evaluation experiment. The hyperparameter tuning is performed by a \texttt{Optuna} study set to maximize its objective function, shown in \cref{lst:objective_function}.

\begin{lstlisting}[float, language=Python, caption={Objective function used for hyperparameter tuning of the evaluated models}, label={lst:objective_function}]
def objective(trial, model_class, search_space_class, X_opt, y_opt, batch_size):
    params = search_space_class().sample_parameters(trial)

    try:
        model = model_class(**params)
    except Exception as e:
        raise optuna.exceptions.TrialPruned()

    burn_in_idx = int(0.05 * len(X_opt))
    y_pred_all = []
    num_batches = len(X_opt) // batch_size

    t0 = time.process_time_ns()

    try:
        for b in range(num_batches):
            start_idx = b * batch_size
            end_idx = start_idx + batch_size
            X_batch = X_opt[start_idx:end_idx]

            preds = model.predict(X_batch)
            y_pred_all.extend(preds)
            model.fit(X_batch)

    except Exception as e:
        raise optuna.exceptions.TrialPruned()

    t_total_sec = (time.process_time_ns() - t0) / 1e9

    y_pred_eval = np.array(y_pred_all)[burn_in_idx:]
    y_opt_eval = y_opt[: len(y_pred_all)][burn_in_idx:]

    ari = adjusted_rand_score(y_opt_eval, y_pred_eval)

    l2_time_penalty = 1e-3 * t_total_sec
    return ari - l2_time_penalty
\end{lstlisting}

Such objective function may be expressed as in \cref{alg:hyperparameter_tuning_objective_function}.

\begin{algorithm}[htbp]
\caption{Objective function for hyperparameter tuning of the evaluated models}
\label{alg:hyperparameter_tuning_objective_function}
\begin{algorithmic}[1]
\Require $X_{opt}$ the input samples for hyperparameter tuning, $y_{opt}$ the ground truth labels for hyperparameter tuning, $batch\_size$ the size of the batches to be processed, $model\_class$ the class of the model to be evaluated, $search\_space\_class$ the class that defines the search space for the model's hyperparameters, $trial$ the current trial of the hyperparameter tuning process
\Ensure $score$ the score to be maximized by the hyperparameter tuning process
\State query $params$ from the $trial$ select by the Optuna study, according to the search space defined by $search\_space\_class$
\State initialize $model$ with $params$
\State perform the prequential execution and capture its execution time
\State drop the initial 5\% of the predictions to avoid penalizing the model for its initial learning phase
\State compute the adjusted rand index $ari$ between the predictions and the ground truth labels
\State return the regularized score $score = ari - \lambda \cdot t_{total}$, where $\lambda$ is a regularization factor that penalizes the execution time of the model
\end{algorithmic}
\end{algorithm}

This tuning strategy's goal is to both reduce error- and bias-prone subjective decisions regarding the choice of hyperparameters and to prevent the selection of parameters that provide a small increase in the score at the cost of a significant increase in the execution time.

\subsection{Multi-run Statistics}

For empirical studies, statistics over multiple experiment runs are required to account for the stochastic nature of the models and the data. In this reassessment, each run starts at the randomized stream generation, goes through hyperparameter tuning, and ends with the evaluation of the tuned model over the remaining samples of the stream. Although the original work aggregates the results of multiple runs under the mean and standard deviation pair, this reassessment uses performs such aggregation under the median and interquartile range (IQR) pair. The reasons for this choice are:

\begin{enumerate}
    \item The tuning phase may find local optima in the hyperparameter space, specially since it is performed over a randomized stream, which may lead to outlier runs with significantly worse performance than the actual performance of the model. The median and IQR are more robust to outliers than the mean and standard deviation, which may be significantly affected by those outlier runs.
    \item \textbf{Matplotlib}'s logarithmic scale plotting does not support negative values, which the lower bounds may assume when computed as $\mu - \sigma$. $Q_1$, however, is guaranteed to greater than or equal to the minimum value of the sample, which is always non-negative for the metrics that are ploted in logarithmic scale for this reassessment.
\end{enumerate}

It is assumed that $N=1000$ runs provide enough statistial power to propperly estimate the true performance of the model. Since such quantity imposes a prohibitive combinational cost, the number of runs $k^*$ required to closely approximate this reference is defined as \cref{eq:kneedle}.

\begin{equation}
k^* \;=\; \operatorname*{argmax}_{k \in \{k_{\min},\dots,N-1\}}\;
\frac{\big|(\tilde k_{\max}-\tilde k_{\min})\big(\tilde Y(k)-\tilde Y_{\min}\big) - (\tilde Y_{\max}-\tilde Y_{\min})\big(\tilde k(k)-\tilde k_{\min}\big)\big|}
{\sqrt{(\tilde k_{\max}-\tilde k_{\min})^2 + (\tilde Y_{\max}-\tilde Y_{\min})^2}},
\label{eq:kneedle}
\end{equation}

which is solved by the Kneedle algorithm \cite{satopaa2011kneedle} as the point of maximum distance to the secant line joining the endpoints of the min--max-normalized curve

\begin{align}
\tilde k(k) &= \frac{k - k_{\min}}{k_{\max}-k_{\min}}, &
\tilde Y(k) &= \frac{\hat Y_{\mathrm{med}}(k) - \min_k \hat Y_{\mathrm{med}}(k)}{\max_k \hat Y_{\mathrm{med}}(k) - \min_k \hat Y_{\mathrm{med}}(k)},
\end{align}

where $\hat Y_{\mathrm{med}}$ is a monotonically non-increasing isotonic regression \cite{barlow1972statistical} fit to the global worst-case median-convergence curve

\begin{equation}
\begin{gathered}
Y_{\mathrm{med}}(k) = \max_{c \in \mathcal{C}} \mathrm{NMAE}^{\mathrm{med}}_c(k), \\
\mathcal{C} = \{\text{SCL2}, \text{STR-B1}, \text{STR-B2}\} \times \{\texttt{ARI}, \texttt{Time}, \texttt{Memory}, \texttt{\#Microclusters}\}.
\end{gathered}
\end{equation}

For a configuration $c \in \mathcal{C}$ and subset size $k \in \{k_{\min},\dots,N-1\}$, and $S_{c,k,1},\dots,S_{c,k,B}$ $B$ independent and identicaly distributed draws, uniform over the $\binom{N}{k}$ size-$k$ subsets of $\{1,\dots,N\}$, and subsample statistics

\begin{equation}
\begin{aligned}
m_{c,k,b} = \operatorname{median}\big(\mathcal{D}_c[S_{c,k,b}]\big), \qquad
q_{c,k,b} = Q_3\big(\mathcal{D}_c[S_{c,k,b}]\big) - Q_1\big(\mathcal{D}_c[S_{c,k,b}]\big), \\ b=1,\dots,B,
\end{aligned}
\end{equation}

the normalized mean absolute errors

\begin{align}
\mathrm{NMAE}^{\mathrm{med}}_c(k) = \frac{1}{s_c B}\sum_{b=1}^{B} \big|m_{c,k,b}-\tilde m_c\big|, \qquad
\mathrm{NMAE}^{\mathrm{iqr}}_c(k) = \frac{1}{s_c B}\sum_{b=1}^{B} \big|q_{c,k,b}-\tilde q_c\big|
\end{align}

are Monte Carlo estimates, with $B$ samples, of $\mathbb{E}_{S}\big[\,|\operatorname{stat}(\mathcal{D}_c[S])-\operatorname{stat}(\mathcal{D}_c)|\,\big]/s_c$, the expectation taken over $S$ uniform on size-$k$ subsets of $\{1,\dots,N\}$ \cite{robert2004monte}.

The reference statistics and scale are

\begin{align}
\tilde m_c &= \operatorname{median}(\mathcal{D}_c), &
\tilde q_c &= Q_3(\mathcal{D}_c) - Q_1(\mathcal{D}_c), &
s_c &= \tilde q_c,
\end{align}

with $\mathcal{D}_c$ the finite population of run-level metric values,

\begin{equation}
\mathcal{D}_c = \{x_{c,i}\}_{i=1}^{N} \subset \mathbb{R}, \qquad x_{c,i} = \text{value of metric } c \text{ on run } i.
\end{equation}

For $N=1000$, $B=10^4$, $k_{\min}=3$, $k^* = 94$. \cref{fig:medianiqr_convergence_with_k} shows the convergence of the median and IQR maximum normalized absolute error over $k$ runs and highlights the $k^*$ value. The metrics are captured on the middle batch of the stream, in which the model is assumed to have reached a steady state and the metrics are expected to be stable.

\begin{figure}[thpb]
    \centering
    \includegraphics[width=\textwidth]{MethodologyReassessment/figures/medianiqr_convergence_with_k.png}
    \caption{Convergence of the median and IQR maximum normalized absolute error over $k$ runs. The left plot shows the convergence of the median, while the right plot shows the convergence of the IQR. The vertical dashed line indicates the $k^*$ value, which is the number of runs required to closely approximate the reference statistics obtained from $N=1000$ runs.}
    \label{fig:medianiqr_convergence_with_k}
\end{figure}

\section{Datasets}

The original work organizes the datasets used in its experiments into three categories: static, concept drift, and the synthetic datasets used for the processing time scalability experiments. Although the selected datasets are commonly used in the literature for data stream clustering evaluation \cite{bezerra2016tedacloud,bezerra2020autocloud,zhang2022extension,nguyenLe2026beyondbinary,zubaroglu2023emcstream}, the following subsections discuss how some downsampling, cleaning, ordering, and scaling decisions had a significant and hidden impact on the experiment results and invalidated the conclusions drawn from them regarding real-world online stream clustering scenarios.

\subsection{Static}

In \cite{maia2020evolvclus}, static datasets \textbf{ST-D1} and \textbf{ST-D2} are stated to correspond to datasets introduced in \cite{karypis1999chameleon} to evaluate the performance of the Chameleon clustering algorithm. From the original work's plots, it can be inferred that those corresponds to datasets \textbf{DS4} and \textbf{DS5} from the source paper. The public repository, however, loads its experiment's data from \url{https://query.data.world/s/faarcpz24ukr2g53druxljp4nghhzn} and \url{https://query.data.world/s/zry3yzt4ruwrlonziw2pfkegsdugw2}, which are cleaned, downsampled, scaled, and ordered versions of the original datasets, and no information regarding the preprocessing steps is provided in the original work. Those operations over the dataset guarantee severe data leakage given the streaming nature of the proposed application for which the model is designed. The following experiments investigate the impact of each of those preprocessing steps on the score chosen to evaluate the clustering quality, discussed in \cref{sec:evaluation_metrics}, and on the execution time of the model. Without loss of generality, \textbf{ST4} is chosen as the representative dataset for the experiments.

\subsubsection{Raw Dataset}

The original \textbf{DS4} dataset is loaded from \url{https://raw.githubusercontent.com/deric/clustering-benchmark/master/src/main/resources/datasets/artificial/cluto-t7-10k.arff}. It contains 10000 samples, 2 features, 9 clusters, and significant noise. \cref{fig:raw_ds4} shows a scatter plot of the dataset, where each feature corresponds to one of the axes, and each sample is colored according to its cluster label. In any valid scenario, the clustering model itself must determine which samples are noise with only knowledge of the previous samples, or not handle it at all \cite{akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline,zhang2022extension,zubaroglu2023emcstream,kaufman2012leakage,kapoor2023leakage}.

\section{Evaluation Metrics} \label{sec:evaluation_metrics}

The original work evaluates its proposed model against the selected benchmark models under three metrics: the adjusted rand index, the execution time, and the memory footprint. The following subsections explain how those metrics are computed in it and discuss the impacts of some choices on the validity of the experiments and the reliability of the results.

\subsection{ARI}

The adjusted rand index is a widely used metric for evaluating the quality of clustering algorithms \cite{hubert1985ari}. Because it is an external metric \cite{halkidi2001validation}, it does not depends on the data distribution or the number of clusters, which makes it suitable for evaluating the performance of clustering algorithms in a streaming setting over non-gaussian datasets. The predictions over which it is computed in the original work, and the analysis of the results, however, do not match the standard practice for evaluating clustering algorithms in streaming or offline settings \cite{akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline,zhang2022extension,zubaroglu2023emcstream}. \cref{sec:prequential_sequential_offline_evaluation} discusses the protocol under which the models' predictions are captured.

Even if computed under suitable evaluation protocols, a single "mean plus standard deviation" over multiple runs is not descriptive for algorithms that are expected to handle evolving data streams. Some questions that are not answered by such measure are:

\begin{itemize}
    \item How much information does a model require to reach a satisfactory performance?
    \item Does its performance degrade over time, and if so, how much?
\end{itemize}

\cref{fig:similar_stats_different_shapes} shows three hypothetical evolutions of the ARI over evaluation batches. For each of them, the answer to the questions above is different, but their central tendency and dispersion measures are the same. The first evolution shows a model that slowly but consistently improves its performance over time, the second shows a model that quickly reaches a high score but then degrades over time, and the third shows a model scores randomly over the batches. The first model is likely the best choice for a real-world application, but the mean and standard deviation of the ARI do not provide enough information to make such decision.

\begin{figure}[thpb]
    \centering
    \includegraphics[width=\textwidth]{MethodologyReassessment/figures/similar_stats_different_shapes.png}
    \caption{Three hypothetical evolutions of the ARI over evaluation batches. The left plot shows slowly increasing curve, the middle plot shows a curve that quickly reaches a peak and then degrades, and the right plot shows a random curve. All three curves have the same mean and standard deviation, but their shapes are different, which leads to different interpretations of the model's performance.}
    \label{fig:similar_stats_different_shapes}
\end{figure}

The original work handles this lack of information with plots of the evolution of the ARI over the evaluation batches for the concept drift datasets, but not for the static datasets. Furthermore, visual interpretation of the plots is not a reliable approach, as it is subjective, prone to error and bias, and does not provide a quantitative measure of the model's performance over time. To address this issue, this reassessment proposes the following metrics to complement the overall ARI and provide a better understanding of the model's performance over time:

\subsubsection{Penultimate batch's ARI}

For each run, the penultimate evaluation batch's ARI is computed. Such score is expected to quantitatively answer the second of the previous questions. It represents the model's performance after it has processed many samples and the concept drift, if any, has occurred. A model that is able to adapt to concept drift is expected to achieve a high ARI in the penultimate batch, while a model that is not able to adapt to concept drift is expected to achieve a low ARI in the penultimate batch. The penultimate batch is selected instead of the last batch to avoid the need to handle the case in which the last batch is not a full batch, which would require additional decisions regarding how to handle it.

\subsubsection{Fifth batch's ARI}

For each run, the fifth evaluation batch's ARI is computed. Such score is expected to quantitatively answer the first of the previous questions. It represents the model's performance after it has processed a small number of samples and before any concept drift has occurred. A model that is able to learn quickly is expected to achieve a high ARI in the fifth batch, while a model that is not able to learn quickly is expected to achieve a low ARI in the fifth batch. The fifth batch is arbitrarily selected.

\subsubsection{Difference between the highest ARI and the ARI of the last batch}

For each run, the difference between the highest ARI and the ARI of the last evaluation batch is computed. It represents specifically the robustness of the model to concept drift. The highest score is expected to be reached in a steady state, before any concept drift has occurred. Since concept drift is expected to degrade the model's performance, this metric is expected to have a smaller value for a model that is less harmed by it than for a sensible that is more sensible to it.

\cref{tab:complementary_scores_on_the_hypotheticals} shows the values of the proposed complementary scores for the three hypothetical evolutions of the ARI shown in \cref{fig:similar_stats_different_shapes}. The first model, which slowly improves its performance over time, has a low ARI at the fifth batch ($0.005$), the optimal ARI at the penultimate batch ($1.000$), and zero difference between its highest and final batch scores ($0.000$). The second model, which quickly reaches a high score but then degrades over time, has the highest ARI at the fifth batch ($0.463$), a low ARI at the penultimate batch ($0.081$), and a large difference between its highest and final batch scores ($0.922$). The third model coincidently yields an ARI of $0.000$ for both the fifth and penultimate batches, while presenting the maximum possible difference between its highest and final batch scores ($1.000$). It is important to note that a randomly scoring model may achieve a high ARI in a single batch, which is handled by the multi-run aggregation statistics discussed in \cref{subsec:multi_run_statistics}.

\begin{table}
    \centering
    \begin{tabular}{|c|c|c|c|}
        \hline
        Curve & Penultimate batch & Fifth batch & Highest $-$ Last \\
        \hline
        Smooth & \textbf{1.000} & 0.005 & \textbf{0.000} \\
        Spike & 0.081 & \textbf{0.463} & 0.922 \\
        Plateau & 0.000 & 0.000 & 1.000 \\
        \hline
    \end{tabular}
    \caption{Complementary scores for the hypothetical score curves. The bold values indicate the best performance for each metric.}
    \label{tab:complementary_scores_on_the_hypotheticals}
\end{table}

Thus, for the datasets that are not scalability-oriented, this reassessment reports the overall ARI, the penultimate batch's ARI, the fifth batch's ARI, and the difference between the highest ARI and the ARI of the last batch. For the scalability-oriented datasets, tables are not reported. Instead, ARI is reported and analyzed through plots of the evolution of the ARI over the evaluation batches, as in the original work.

\subsection{Complete Runtime} \label{subsec:complete_runtime}

In \cite{maia2020evolvclus}, execution time is only assessed on for the scalability-oriented datasets, and only reported through a plot of execution time per samples versus the feature dimension. Furthermore, since only the mean accross the multiple runs is reported, it is not possible to assess the variability of this metric. This reassessment evaluates and compares fitting and prediction separately, and reports the following analysis:

\begin{itemize}
    \item For the datasets that are not scalability-oriented, the median and the $(Q_{1}, Q_{3})$ pair of the cumulative execution time for each stage are captured and reported for each model in suitable tables. This allows for a better understanding of the variability of the execution time and the impact of the dataset characteristics on it.
    \item For the scalability-oriented datasets, the median and the $(Q_{1}, Q_{3})$ pair of each stage are captured and reported for each model in the following plots:
    \begin{itemize}
        \item Execution time versus the number of samples, for each of two fixed feature dimensions (2 and 64).
        \item Execution time versus the feature dimension, for each of two fixed batch indexes (10 and last - 1).
    \end{itemize}
    This report strategy's goal is to further investigate how the feature dimension impacts on the sample-scalability of the evaluated models, and how the number of samples impacts on the feature-scalability of the evaluated models. Median and quartiles are selected because preeliminary experiments show that a logarithmic scale is more suitable for this metric -- since the models differ by orders of magnitude -- and the high variability of the execution time increase the risk of negative bounds when defined as $\mu - \sigma$. Because \textbf{Matplotlib}'s logarithmic scale does not support negative values, the quartile-pair is preferred to avoid artificially clipping the lower bound of the error bars to zero, since the quartiles are guaranteed to be bounded by the values actually observed in the experiments.
\end{itemize}

\subsection{Memory Usage}

The original work reports memory consumption only through a plot of memory usage versus the number of samples for \textbf{STR-B1} for a single run. This reassessment evaluates and compares the memory usage of each model for all datasets, and reports the following analysis:

\begin{itemize}
    \item For the datasets that are not scalability-oriented, the median and the $(Q_{1}, Q_{3})$ pair of the maximum and the penultimate batch's memory usage are captured and reported for each model in suitable tables. \section{Prequential, Sequential, and Offline Evaluation} \label{sec:prequential_sequential_offline_evaluation}

\cite{maia2020evolvclus} states, in section 5.2.1, that it applies prequential evaluation to assess the performance of the evaluated models in its experiments: "\textit{For each data set and clustering algorithm, the Prequential method is applied. In this method, each instance can be used to test before it is used for training.}". Such approach is, indeed, the standard practice for evaluating clustering algorithms in a streaming setting \cite{akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline}, since "\textit{the purpose of statistical inference is to make sequential probability forecasts for future observations, rather than to express information about parameters.}" \cite{dawid1984prequential},

However, two observations show that prequential evaluation is implemented in any of the original work's experiments. First, the code in the public repository shows two distinct evaluation protocols, neither of which is prequential evaluation, and a naming misguidance.

For \textbf{ST-D1} and \textbf{ST-D2}, the implemented protocol is shown in \cref{snippet:original_work_static_evaluation_protocol},

\begin{lstlisting}[float, language=Python, caption={Original work's implementation of the evaluation protocol for static datasets}, label={snippet:original_work_static_evaluation_protocol}]
  X = stream_df[['x', 'y']].values
  y = stream_df['class'].values
  evol_model = EvolvingClustering.EvolvingClustering(variance_limit=0.0006, debug=False)

  evol_model.fit(X)
  y_hat = evol_model.predict(X)

  error = adjusted_rand_score(y, y_hat)
\end{lstlisting}

which learns the entire dataset before performing the inferences over the exact same samples. Even though the work recognizes that it performs offline evaluation for the static datasets, such protocol is not standard practice for evaluating clustering algorithms in an offline setting \cite{kaufman2012leakage,kapoor2023leakage,arias2024improved,halkidi2001validation}, for which cross-validation is one of the preferred approaches \cite{stone1974cross,kohavi1995study}.

For the remaining datasets, the implemented protocol is exemplified in \cref{snippet:original_suposed_prequential_evaluation_protocol},

\begin{lstlisting}[float, language=Python, caption={Original work's implementation of the evaluation protocol for concept drift and scalability-oriented datasets}, label={snippet:original_suposed_prequential_evaluation_protocol}]
  X = stream_df[['X1', 'X2']].values
  y = stream_df['class'].values
  evol_model = EvolvingClustering.EvolvingClustering(macro_cluster_update=1,  variance_limit=0.001, debug=False)
  accum_error, error_list = Benchmarks.prequential_evaluation(evol_model, X, y, adjusted_rand_score, train_size, window_size)
\end{lstlisting}

The name of the function \texttt{prequential\_evaluation} may suggest that it implements prequential evaluation, but its definition is provided in \cref{snippet:original_work_prequential_evaluation_function}:

\begin{lstlisting}[float, language=Python, caption={Original work's implementation of the function named \texttt{prequential\_evaluation}}, label={snippet:original_work_prequential_evaluation_function}]
def prequential_evaluation(
    method, data, labels, metric, train_size, window_size=1, fading_factor=1, adjust_labels=0, elapsed_time=False,
):
    test_end = 0
    index = 0
    limit = len(labels)
    accumulated_error = 0
    error_list = []
    elapsed_time_list = []
    memory_usage_list = []

    while test_end < limit:
        train_start, train_end, test_start, test_end = getDataIndex(
            index, train_size, window_size, limit
        )
        train_data = data[train_start:train_end]
        test_data = data[test_start:test_end]
        index = test_start

        if elapsed_time:
            time_start = time.time()
        method.fit(train_data)
        y_hat = method.predict(test_data)
        y = labels[test_start:test_end]

        if elapsed_time:
            time_end = time.time()
            elapsed_time_list.append(time_end - time_start)

        if adjust_labels == 2 or (index == test_start and adjust_labels == 1):
            y_hat = util.adjust_labels(y_hat, y)

        error = metric(y, y_hat)
        accumulated_error += fading_factor * error
        error_list.append(error)

        process = psutil.Process(os.getpid())
        memory_usage_list.append(process.memory_info().rss / 1000.0)

    return {
        "accumulated_error": accumulated_error, "error_list": error_list, "elapsed_time_list": elapsed_time_list, "memory_usage_list": memory_usage_list,
    }
\end{lstlisting}

of which the excerpt \cref{snippet:original_work_prequential_evaluation_function_steps} shows that the model is trained on the batch before performing the estimation of the labels of its samples:

\begin{lstlisting}[float, language=Python, caption={Excerpt of the original work's implementation of the function named \texttt{prequential\_evaluation}}, label={snippet:original_work_prequential_evaluation_function_steps}]
        if elapsed_time:
            time_start = time.time()
        method.fit(train_data)
        y_hat = method.predict(test_data)
        y = labels[test_start:test_end]
\end{lstlisting}

which is exactly the opposite of prequential evaluation, in which the model is evaluated on the batch before being trained on it.

The second hint that the original work does not implement prequential evaluation is in its own batchwise plots. Since, under prequential evaluation, predictions are performed before learning, the ARI of the first batch is expected to be near 0.0, as the model has not yet learned anything about the data. \cref{fig:original_curves} shows the $\text{ARI}(\text{first\_batch}) > 0.5$ for all the reported experiments, and $> 0.8$ for 10 out of 15 curves. Thus, independently of external code inspection, those results cast doubt on the validity of the work's conclusions.

It is worth noting that, for the performed sequential evaluation, the optimal model is the one that simply memorizes the label for the sample in each coordinate \cite{aliferis2024overfitting,bayat2025pitfalls}. Such overfitted model, however, is shown to poorly generalize to unseen samples, and is not suitable for real-world applications.

This reassessment's only protocol, applied throughout all experiments, is prequential evaluation. For each 100-sample batch, the samples' labels are predicted before the model is trained on them. The predicted labels are then compared to the ground truth labels to compute the ARI, and the execution time and memory usage are measured for both the prediction and training stages.

\section{Statistical Significance Tests} \label{sec:statistical_significance}

To rigorously classify models as indistinguishable from the optimal or pessimal algorithms for a given metric and dataset, this reassessment adopts a non-parametric statistical evaluation pipeline \cite{demsar2006statistical}. To prevent trivial floating-point artifacts and hardware-level noise from artificially inflating the statistical power of rank-based tests, all metric observations are first discretized to a priori thresholds of practical relevance:

\begin{align}
\text{ARI}_\text{disc} &= 10^{-3} \lfloor 10^3 \cdot \text{ARI} \rceil, & \text{Time}_\text{disc} \left[\text{ms}\right] &= 10 \lfloor \text{Time} \left[\text{ms}\right] / 10 \rceil, \nonumber \\ \
\text{Memory}_\text{disc} \left[\text{B}\right] &= 1024 \lfloor \text{Memory} \left[\text{B}\right] / 1024 \rceil, & \text{MC}_\text{disc} &= \lfloor \text{MC} \rceil
\end{align}

The evaluation proceeds by assessing the global divergence of the $C$ evaluated models across the $N=94$ paired runs via the Friedman omnibus test \cite{friedman1937use} at a significance level of $\alpha = 0.05$. If the omnibus null hypothesis is not rejected, all models are declared statistically indistinguishable. If the null hypothesis is rejected, the models yielding the optimal and pessimal sample medians, denoted $m_{\text{best}}$ and $m_{\text{worst}}$ respectively, are isolated as references. Post-hoc pairwise comparisons are then conducted strictly between these references and the remaining $C-1$ candidate models using the paired Wilcoxon signed-rank test \cite{wilcoxon1945individual}. The resulting arrays of $p$-values are adjusted using the Holm-Bonferroni step-down procedure \cite{holm1979simple} to tightly control the family-wise error rate.

Because the Wilcoxon signed-rank test exhibits extreme sensitivity at sample sizes of $N=94$, frequently rejecting the point-null hypothesis for infinitesimal differences of no practical consequence, a dual-criterion thresholding strategy is applied. A model $m_i$ is deemed strictly distinguishable from the reference $m_{\text{ref}} \in \{m_{\text{best}}, m_{\text{worst}}\}$:

\begin{equation}
D(m_i, m_{\text{ref}}) \iff (p_{\text{adj}} < \alpha) \land (\vert d \vert \ge 0.147),
\end{equation}

where $p_{\text{adj}}$ is the Holm-Bonferroni adjusted $p$-value, $d$ is Cliff's Delta \cite{cliff1993dominance}, and $\vert d \vert \ge 0.147$ is the empirical boundary for a non-negligible effect size \cite{romano2006appropriate}.

Contrasting both model subsets, no single one is uniformly preferable across all metrics. The original work's model set is stronger under clustering quality, as \textbf{StreamKM} and \textbf{CluStream} are the most frequent ARI winners, but it is comparatively costly in memory and microcluster count. The TEDA-based set, excluding \textbf{MicroTEDAClus} and \textbf{AutoCloud}, trades clustering quality for efficiency: \textbf{TEDACloud} dominates the memory footprint, \textbf{CEDAS} dominates fitting time, and \textbf{DenStream} dominates the microcluster count, yet \textbf{CEDAS} is indistinguishable from the worst model on five of the six datasets under the overall ARI, despite being fast and compact. Within the complete model set, \textbf{StreamKM} is the closest to an overall best model, being the sole or tied-fastest predictor on all six datasets, competitive to the best model on most ARI tables, and never indistinguishable from the worst model for memory or microcluster count, although it is not dominant, since \textbf{TEDACloud} surpasses it in memory, \textbf{CEDAS} surpasses it in fitting time, and \textbf{CluStream} occasionally surpasses it in ARI. Conversely, \textbf{MicroTEDAClus} and \textbf{AutoCloud} are the clear laggards, each indistinguishable from the worst model on a majority of datasets across most metrics, with \textbf{MicroTEDAClus} further exhibiting the dimensionality-driven collapse in quality, time, and memory discussed throughout this section. These results support a trade-off between clustering quality and computational footprint rather than a strict dominance relation among models or subsets, except at the lower end, where \textbf{MicroTEDAClus} and \textbf{AutoCloud} are dominated by nearly every alternative under nearly every metric.
