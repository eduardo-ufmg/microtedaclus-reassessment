\chapter{Methodology Reassessment}
\label{chap:methodology_reassessment}

The \textit{Evolving clustering algorithm based on mixture of typicalities for stream data mining} paper presents promising results for the microTEDAclus model \cite{maia2020evolvclus}. Before conclusions can be drawn from those results, however, it is important to assess the methodology used in the original work. In this chapter, only its methodology is reviewed, since the following paper, \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile} assumes its validity and does not perform further investigation on it.

The next sections examine weaknesses from the evaluated model implementation to the experiments protocol, including the evaluation metrics and procedures. The goal of this reassessment is to identify potential issues in the original work's methodology that could affect the validity of its results and conclusions. By doing so, a more rigorous and accurate evaluation of the microTEDAclus model can be conducted, leading to more reliable conclusions about its performance and applicability in real-world scenarios.

\section{Model Implementation} \label{sec:model_implementation}

In the fifth section of the original work, \textbf{Methodology and experiments}, \cite{maia2020evolvclus} provides a URL to the public GitHub repository where the code for the experiments can be found: \url{https://github.com/cseveriano/evolving_clustering}. To ensure persistence of the code, a fork of the original repository was created at the commit \texttt{50dd2b4}, which is the last commit to the repository at the time of this reassessment \cite{eduardo2026evolvingclustering}. The implementation of the microTEDAclus model is found in the \texttt{src/models/evolving/EvolvingClustering.py} file of the repository.

It is important to note that the implementation of the microTEDAclus model found in the public repository is not the same as the one described in the original work, but is the one that, when submitted to the repository experiments, produced the results shown in the original work. A closer inspection of the code reveals that said implementation have characteristics that are similar to the ones described in the updated version of microTEDAclus, which is presented in the PHD thesis \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile}. Furthermore, it handles the outlier-condition logic's problem stated in \cref{sss:incorrect_condition_logic}, but introduces mathematical errors in the implementation of expressions \cref{eq:recursive_eccentricity} and \cref{eq:normalized_typicality}, which are the core of the microTEDAclus model. This is a problem because the results of the experiments are not comparable to the ones presented in the original work, and the conclusions drawn from those results may not be valid.

The most notable and critical change from the paper's formulation to the implementation is the introduction of an explicit decayment logic, specifically the one described in \cite{galindo2021lastmile}. The model constructor's signature is seen in \cref{snippet:maia_implementation_constructor}.

\begin{lstlisting}[float, language=Python, caption={Constructor of the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_constructor}]
def __init__(self, macro_cluster_update=1,
                verbose=0, variance_limit=0.001, decay = 100, debug=False, plot_graph=False):
    self.verbose = verbose
    self.total_num_samples = 0
    self.micro_clusters = []
    self.macro_clusters = []
    self.active_macro_clusters = []
    self.graph = nx.Graph()
    self.active_graph = nx.Graph()
    self.variance_limit = variance_limit
    self.macro_cluster_update = macro_cluster_update
    self.debug = debug
    self.plot_graph = plot_graph
    self.changed_micro_clusters = []
    self.fading_factor = 1 / decay
\end{lstlisting}

The introduced factor, $\text{fading\_factor} = \frac{1}{\text{decay}}$, corresponds to the $\rho$ parameter of the decayment logic described in \cite{galindo2021lastmile}, which is a value between 0 and 1 that determines the rate at which the model forgets old data. It is used in two distinct methods of the implementation. In \cref{snippet:maia_implementation_prune_microclusters}, it linearly decays the \texttt{life} of the microclusters that were considered 'not active' in the current \texttt{fit} iteration. Such functionality loosely corresponds to the one described in \cite{galindo2021lastmile}, but does not match it exactly; the paper states that the decayment is applied to the microclusters that are not updated by the sample being processed, while the "activeness" of a microcluster is determined in the macrocluster construction phase, and depends only on the comparison between the microcluster's and the macrocluster's densities.

\begin{lstlisting}[float, language=Python, caption={Pruning of microclusters in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_prune_microclusters}]
def prune_micro_clusters(self):
    for mc in self.micro_clusters:

        if not mc["active"]:
            mc["life"] = mc["life"] - self.fading_factor

            if mc["life"] < 0:
                self.micro_clusters.remove(mc)

                if mc in self.changed_micro_clusters:
                    self.changed_micro_clusters.remove(mc)

                self.graph.remove_node(mc["id"])
\end{lstlisting}

The second method where the fading factor is used is \cref{snippet:maia_implementation_update_life}. In this method, the fading factor acts as a scaling coefficient for a dynamic reward or penalty. It evaluates the Euclidean distance of the new sample to the micro-cluster's center relative to its standard deviation. If the sample is closer than the standard deviation, \texttt{life} increases, otherwise it decreases. The fading factor scales the amount of increase or decrease, which means that the model will forget old data faster if the fading factor is higher.

\begin{lstlisting}[float, language=Python, caption={Update of microclusters' life in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_update_life}]
    def update_life(self, xk, micro_cluster):
        previous_mean = micro_cluster["mean"]
        previous_var = micro_cluster["variance"]
        if previous_var > 0:
            d = EvolvingClustering.get_euclidean_distance(xk, previous_mean)
            dist = np.sqrt(np.sum(d))
            rt = np.sqrt(previous_var)
            micro_cluster["life"] = micro_cluster["life"] + (((rt - dist) / rt) * self.fading_factor)
        else:
            micro_cluster["life"] = 1
\end{lstlisting}

Such decayment logic is not present neither in the original work nor in the updated version of microTEDAclus, and its introduction in the implementation found in the public repository is not justified or explained in any of those works. This is a problem because it introduces a significant change to the model's behavior that is not accounted for in the original work, and it may affect the results of the experiments and the conclusions drawn from them.

Another significant change from the paper's formulation to the implementation is the handling of microcluster activation. \cref{info:microcluster_activation_criterion} and \cref{critique:use_of_unstable_density} present the criterion and use for microcluster activation stated in the original work. The implementation's procedure deviates from it and is described in \cref{alg:microcluster_activation_criterion_pseudocode}. Note that this pseudocode corresponds to the current work's interpretation of the code provided in the public repository, and it is not acknowledged or explained in neither the original work or the updated version of microTEDAclus' presentation.

\begin{algorithm}[htbp]
\caption{Microcluster activation criterion used in the implementation found in the public repository}
\label{alg:microcluster_activation_criterion_pseudocode}
\begin{algorithmic}[1]
\Require $m_i$, $i = 1, 2, \dots, n$ (the set of all microclusters)
\Ensure $\mathcal{M}_j, j = 1, 2, \dots, m$ (the set of macroclusters)
\State Construct the graph $\mathbb{G}_0$ by connecting microclusters that satisfy the intersection condition described in \cref{eq:microcluster_intersection_condition}
\State Build a macrocluster $\mathcal{M}_j$ for each connected component of $\mathbb{G}_0$
\For{each macrocluster $\mathcal{M}_j$}
    \State Compute its microclusters' activation according to \cref{critique:use_of_unstable_density}
\EndFor
\State Capture the active graph $\mathbb{G}_1$ by removing the non-active microclusters from $\mathbb{G}_0$
\State Build a macrocluster $\mathcal{M}_j$ for each connected component of $\mathbb{G}_1$
\end{algorithmic}
\end{algorithm}

Hence, it can be inferred that, because $\mathbb{G}_0$ is subject to the ill condition of microcluster collapse, predicted by the original work, a second graph-building pass is performed over the microclusters considered to be active according to \cref{critique:use_of_unstable_density}. The resulting graph, $\mathbb{G}_1$, is expected to be secured from the overlap condition. The macroclusters built from it are the output of the macrocluster construction phase. Not only this change deviates from the original work's formulation, but it also introduces a significant increase in the computational complexity of the macrocluster construction phase, which may affect the results of the experiments and the conclusions drawn from them.

The process is performed by \cref{snippet:maia_implementation_update_macroclusters}, which calls \cref{snippet:maia_implementation_define_macroclusters} to build the macroclusters from the graph $\mathbb{G}_0$ followed by \cref{snippet:maia_implementation_define_activations} to determine the active microclusters, capture the active graph $\mathbb{G}_1$, and extract the final macroclusters from it.

\begin{lstlisting}[float, language=Python, caption={Update of macroclusters in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_update_macroclusters}]
def update_macro_clusters(self):
    self.define_macro_clusters()
    self.define_activations()
\end{lstlisting}

\begin{lstlisting}[float, language=Python, caption={Definition of macroclusters from the graph $\mathbb{G}_0$ in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_define_macroclusters}]
def define_macro_clusters(self):
    for mi in self.changed_micro_clusters:
        for mj in self.micro_clusters:
            if mi["id"] != mj["id"]:
                edge = (mi["id"],mj["id"])
                if EvolvingClustering.has_intersection(mi, mj):
                    self.graph.add_edge(*edge)
                elif EvolvingClustering.nodes_connected(mi["id"],mj["id"], self.graph):
                    self.graph.remove_edge(*edge)

    self.macro_clusters = list(nx.connected_components(self.graph))
    self.changed_micro_clusters.clear()
\end{lstlisting}

\begin{lstlisting}[float, language=Python, caption={Definition of active microclusters and macroclusters from the graph $\mathbb{G}_1$ in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_define_activations}]
def define_activations(self):
    self.active_graph = self.graph.copy()
    for mg in self.macro_clusters:
        num_micro = len(mg)
        total_density = 0
        for i in mg:
            dens = next(item["density"] for item in self.micro_clusters if item["id"] == i)
            total_density += dens
        mean_density = total_density / num_micro
        for i in mg:
            mi = next(item for item in self.micro_clusters if item["id"] == i)
            mi["active"] = (mi["num_samples"] > 2) and (mi["density"] >= mean_density)
            if not mi["active"]:
                self.active_graph.remove_node(mi["id"])
    self.active_macro_clusters = list(nx.connected_components(self.active_graph))
\end{lstlisting}

\cref{snippet:maia_implementation_is_outlier} implements \cref{eq:outlier_condition} and substitutes \cref{critique:incorrect_condition_logic} by \cref{eq:corrected_condition_logic_for_outliers}.

\begin{lstlisting}[float, language=Python, caption={Outlier detection in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_is_outlier}]
def is_outlier(self, s_ik, var_ik, norm_ecc):
    if s_ik < 3:
        outlier = (var_ik > self.variance_limit)
    else:
        mik_sik = 3 / (1 + math.exp(-0.007 * (s_ik - 100)))
        outlier_limit = ((mik_sik ** 2) + 1) / (2 * s_ik)
        outlier = (norm_ecc > outlier_limit)
    return outlier
\end{lstlisting}

Finally, \cref{eq:recursive_eccentricity} and \cref{eq:normalized_typicality} are implemented as \cref{snippet:maia_implementation_get_eccentricity} and the previous to last expression of \cref{snippet:maia_implementation_calculate_membership}, respectively.

\begin{lstlisting}[float, language=Python, caption={Eccentricity calculation in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_get_eccentricity}]
def get_eccentricity(x, num_samples, mean, var):
    if var == 0 and num_samples > 1:
        result = (1/num_samples)
    else:
        a = mean - x
        result = ((1 / num_samples) + ((np.linalg.norm(a) * 2 / len(a)) ** 2 / (num_samples * var)))

    return result
\end{lstlisting}

The mathematical expansion of the main expression in \cref{snippet:maia_implementation_get_eccentricity} is \cref{eq:maia_implementation_eccentricity_eq}, which is fundamentally different from \cref{eq:recursive_eccentricity}.

\begin{equation}
    \xi^i\left(x\right) = \frac{1}{S^i_k} + \frac{4\lVert\mu^i_k - x\rVert^2}{d^2S^i_k\left(\sigma^i_k\right)^2}
    \label{eq:maia_implementation_eccentricity_eq}
\end{equation}

\begin{lstlisting}[float, language=Python, caption={Membership calculation in the microTEDAclus implementation found in the public repository}, label={snippet:maia_implementation_calculate_membership}]
def calculate_membership(x, active_micro_clusters):
    total_density = 0
    for m in active_micro_clusters:
        total_density += m["density"]

    mb = 0
    for m in active_micro_clusters:
        d = m["density"]

        t = 1 - EvolvingClustering.get_normalized_eccentricity(x, m["num_samples"], m["mean"], m["variance"])
        mb += (d / total_density) * t
    return mb
\end{lstlisting}

The expression for the intermediary typicality calculation in \cref{snippet:maia_implementation_calculate_membership} cannot be mathematically rewritten to match \cref{eq:normalized_typicality}, and is not equivalent to it.

The updated implementation of microTEDAclus, which is presented in the PHD thesis \textit{Mineração de Dados Aplicada a Problemas de Last-Mile na Logística} \cite{galindo2021lastmile}, was provided by the work's author, but is not publicly available. Its main improvements from the original implementation are the introduction of partial support to the use of the cossine distance as distance metric, the refactor of the decayment logic, and the extraction of the microcluster structure to a separate class.

\section{Benchmark Models}

\subsection{Benchmark Models Implementation Used in the Original Work}

In it's experiments, the original work compares the proposed microTEDAclus model against three benchmark models: DenStream \cite{cao2006density}, CluStream \cite{aggarwal2003framework}, and StreamKM++ \cite{ackermann2012streamkmpp}, commonly used in the literature for data stream clustering evaluation \cite{hyde2017fully,akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline} as benchmark models. The validity of the experiments, however, depends on the implementation and execution of those models. As stated in the article and verified in the public repository, the implementations of those models are sourced from the \texttt{R} package \texttt{streamMOA} through the binding provided by \texttt{rpy2}.

However, because \texttt{streamMOA} is a wrapper for the Java-based MOA framework \cite{streamMOA2024}, two layers of interface overhead are introduced in the execution of the benchmark models. Such overhead is expected to have a significant impact on both the execution time and the memory footprint perceived by the \texttt{Python} experiment orchestrator. To verify such hypothesis, a benchmarking experiment was conducted as described in \cref{alg:benchmarking_experiment}.

\begin{algorithm}[htbp]
\caption{Benchmarking experiment to evaluate the impact of interface overhead on the execution time and memory footprint of the benchmark models}
\label{alg:benchmarking_experiment}
\begin{algorithmic}[1]
\Require $M$ the set of benchmark models, $n = 100000$ the number of samples to be processed, $d = 10$ the dimensionality of the samples, $C = 5$ the number of classes, $c = 50$ the number of clusters, $r = 8$ the number of runs
\Ensure $T$ the execution time and $F$ the memory footprint of each model
\State $S \gets \texttt{generate\_dataset\_with\_riverRandomRBF}(n, d, C, c)$
\For{each model $m \in M$}
    \State $T_m \gets []$
    \State $F_m \gets []$
    \For{$i = 1$ to $r$}
        \State $t, f \gets \texttt{run\_model\_with\_time\_and\_memory\_measurement}(m, S)$
        \State $T_m.\texttt{append}(t)$
        \State $F_m.\texttt{append}(f)$
    \EndFor
    \State $T[m] \gets \texttt{compute\_statistics}(T_m)$
    \State $F[m] \gets \texttt{compute\_statistics}(F_m)$
\EndFor
\end{algorithmic}
\end{algorithm}

\subsection{TEDACloud and CEDAS}

It is not clear why, even though the original work references TEDACloud \cite{bezerra2016tedacloud} and CEDAS \cite{hyde2017fully}, it does not include them in the experiments. CEDAS's introductory paper points to its official \texttt{MATLAB} implementation in \url{https://rhyde67.github.io/CEDAS/}, which was easily ported to \texttt{Python} and is available in the public repository of this reassessment. TEDACloud's introductory paper does not provide a public implementation, but a \texttt{Python} implementation was derived from the algorithm description in the paper and is also available in this work's public repository. Both implementations are included in this reassessment's experiments.

\subsection{AutoCloud}

AutoCloud's introductory paper \cite{bezerra2020autocloud} was published approximately at the same time as the microTEDAclus paper, thus it is not expected to have been included in the original work's experiments. The algorithm is presented as an improvement over TEDACloud, and since it is a recent and relevant work, it is included in this reassessment's experiments. A \texttt{Python} implementation was derived from the algorithm description in the paper and is available in this work's public repository.

\subsection{Hyperparameter Tuning} \label{subsec:hyperparameter_tuning}

All the models evaluated in this reassessment have hyperparameters that can be tuned to improve their performance, even those for which the introductory paper chooses to use default values. To ensure that any model is not unfairly disadvantaged by the choice of hyperparameters, all the following experiments are preceded by a hyperparameter tuning phase in which the first 20\% of the samples of each stream is extracted to perform a Bayesian optimization \cite{ozaki2025optunahub} search for the best hyperparameters of each model. Such an approach prevents data leakage \cite{kaufman2012leakage,kapoor2023leakage} because the evaluation phase is performed on the unseen remaining 80\% of the samples of the stream. Furthermore, it is basically an automated and safer approach than the one taken by the experiments in the original work, in which the parameters that maximize the score over the entire dataset are selected for the evaluation experiment. The hyperparameter tuning is performed by a \texttt{Optuna} study set to maximize its objective function, shown in \cref{lst:objective_function}.

\begin{lstlisting}[float, language=Python, caption={Objective function used for hyperparameter tuning of the evaluated models}, label={lst:objective_function}]
def objective(trial, model_class, search_space_class, X_opt, y_opt, batch_size):
    params = search_space_class().sample_parameters(trial)

    try:
        model = model_class(**params)
    except Exception as e:
        print(
            f"Error initializing model {model_class.__name__} with params {params}: {e}"
        )
        raise optuna.exceptions.TrialPruned()

    burn_in_idx = int(0.05 * len(X_opt))
    y_pred_all = []
    num_batches = len(X_opt) // batch_size

    t0 = time.process_time_ns()

    try:
        for b in range(num_batches):
            start_idx = b * batch_size
            end_idx = start_idx + batch_size
            X_batch = X_opt[start_idx:end_idx]

            preds = model.predict(X_batch)
            y_pred_all.extend(preds)
            model.fit(X_batch)

    except Exception as e:
        print(f"Error occurred while executing model {model_class.__name__}: {e}")
        raise optuna.exceptions.TrialPruned()

    t_total_sec = (time.process_time_ns() - t0) / 1e9

    y_pred_eval = np.array(y_pred_all)[burn_in_idx:]
    y_opt_eval = y_opt[: len(y_pred_all)][burn_in_idx:]

    ari = adjusted_rand_score(y_opt_eval, y_pred_eval)

    l2_time_penalty = 1e-3 * t_total_sec
    return ari - l2_time_penalty
\end{lstlisting}

Such objective function may be expressed as in \cref{alg:hyperparameter_tuning_objective_function}.

\begin{algorithm}[htbp]
\caption{Objective function for hyperparameter tuning of the evaluated models}
\label{alg:hyperparameter_tuning_objective_function}
\begin{algorithmic}[1]
\Require $X_{opt}$ the input samples for hyperparameter tuning, $y_{opt}$ the ground truth labels for hyperparameter tuning, $batch\_size$ the size of the batches to be processed, $model\_class$ the class of the model to be evaluated, $search\_space\_class$ the class that defines the search space for the model's hyperparameters, $trial$ the current trial of the hyperparameter tuning process
\Ensure $score$ the score to be maximized by the hyperparameter tuning process
\State query $params$ from the $trial$ select by the Optuna study, according to the search space defined by $search\_space\_class$
\State initialize $model$ with $params$
\State perform the prequential execution and capture its execution time
\State drop the initial 5\% of the predictions to avoid penalizing the model for its initial learning phase
\State compute the adjusted rand index $ari$ between the predictions and the ground truth labels
\State return the regularized score $score = ari - \lambda \cdot t_{total}$, where $\lambda$ is a regularization factor that penalizes the execution time of the model
\end{algorithmic}
\end{algorithm}

This tuning strategy's goal is to both reduce error- and bias-prone subjective decisions regarding the choice of hyperparameters and to prevent the selection of parameters that provide a small increase in the score at the cost of a significant increase in the execution time.

\subsection{Multi-run Statistics}

To account for the inherent variability in the performance of the evaluated models, each experiment consists of 20 runs for each set of model, dataset, condition, and such. The results of those runs are aggregated and reported as the median, first quartile, and third quartile of the evaluated metrics. The choice of this statistical approach is justified by two reasons:

\begin{enumerate}
    \item Preliminary experiments exposed the presence of outliers in the results of some models, which significantly harms the reliability of the mean as a measure of central tendency, as well as the interpretability of the standard deviation as a measure of dispersion. The median, first quartile, and third quartile are more robust to outliers and provide a better representation of the distribution of the results.
    \item Timing metrics are ploted in logarithmic scale. Such scale not only makes the mean and standard deviation less interpretable, but also require the clipping of the lower bound of the timing metrics to a small positive value when it is zero or negative. This is because the plotting library used in this work does not support logarithmic scale for non-positive values. The median, first quartile, and third quartile are not affected by this issue, since such metrics are bounded by the actual values of the timing metrics, which are always non-negative.
\end{enumerate}

\section{Datasets}

The original work organizes the datasets used in its experiments into three categories: static, concept drift, and the synthetic datasets used for the processing time scalability experiments. Although the selected datasets are commonly used in the literature for data stream clustering evaluation \cite{bezerra2016tedacloud,bezerra2020autocloud,zhang2022extension,nguyenLe2026beyondbinary,zubaroglu2023emcstream}, the following subsections discuss how some downsampling, cleaning, ordering, and scaling decisions had a significant and hidden impact on the experiment results and invalidated the conclusions drawn from them regarding real-world online stream clustering scenarios.

\subsection{Static}


In \cite{maia2020evolvclus}, static datasets \textbf{ST-D1} and \textbf{ST-D2} are stated to correspond to datasets introduced in \cite{karypis1999chameleon} to evaluate the performance of the Chameleon clustering algorithm. From the original work's plots, it can be inferred that those corresponds to datasets \textbf{DS4} and \textbf{DS5} from the source paper. The public repository, however, loads its experiment's data from \url{https://query.data.world/s/faarcpz24ukr2g53druxljp4nghhzn} and \url{https://query.data.world/s/zry3yzt4ruwrlonziw2pfkegsdugw2}, which are cleaned, downsampled, scaled, and ordered versions of the original datasets, and no information regarding the preprocessing steps is provided in the original work. Those operations over the dataset guarantee severe data leakage given the streaming nature of the proposed application for which the model is designed. The following experiments investigate the impact of each of those preprocessing steps on the score chosen to evaluate the clustering quality, discussed in \cref{sec:evaluation_metrics}, and on the execution time of the model. Without loss of generality, \textbf{ST4} is chosen as the representative dataset for the experiments.

\subsubsection{Raw Dataset}

The original \textbf{DS4} dataset is loaded from \url{https://raw.githubusercontent.com/deric/clustering-benchmark/master/src/main/resources/datasets/artificial/cluto-t7-10k.arff}. It contains 10000 samples, 2 features, 9 clusters, and significant noise. \cref{fig:raw_ds4} shows a scatter plot of the dataset, where each feature corresponds to one of the axes, and each sample is colored according to its cluster label. The noise samples are colored in dark blue and are labeled as \texttt{-1} in the \texttt{.arff} file.

\cref{fig:noise_removed_metrics} shows a slight increase in the ARI of the microTEDAclus model over the noise-removed dataset, which reaches nearly 0.5 from batches 10 to 20, but then drops to nearly 0.25 for the rest of the stream. Although the noise removal step achieves a limited impact on the evaluation metrics, it constitutes a severe form of data leakage \cite{kaufman2012leakage,kapoor2023leakage}. This is because a sample is considered noise if it does not belong to any of the clusters, which is a condition that can only be determined after the clustering process. In any valid scenario, the clustering model itself must determine which samples are noise with only knowledge of the previous samples, or not handle it at all \cite{akinosho2023comparative,wang2023data,rezaei2025,mutambik2024,jahn2026goingoffline,zhang2022extension,zubaroglu2023emcstream,kaufman2012leakage,kapoor2023leakage}.

\subsubsection{Downsampling}

It is performed by randomly selecting 50\% of the samples from the noise-removed dataset, resulting in a dataset with 4604 samples, shown in \cref{fig:downsampled_ds4}.

The scaling step is performed by applying a min-max normalization to the features of the downsampled dataset. Each feature is scaled to the range $[0, 1]$ by subtracting the minimum value and dividing by the range of the feature. \cref{fig:scaled_ds4} shows a scatter plot of the scaled dataset.

\begin{figure}[thpb]

    \includegraphics[width=\textwidth]{MethodologyReassessment/figures/scaled_metrics.png}

\cref{fig:scaled_metrics} shows that scaling recovers the ARI of the microTEDAclus model to over 0.25 for most batches, and significantly reduces the execution time. More importantly, scaling shifts the optimal parameter \texttt{variance\_limit} from $1 < r_0 < 10$ to $0.01 < r_0 < 0.1$. This contradicts the original work's claim that the model is robust to the choice of this parameter, since it is highly dependent on the scale of the data.

Scalling is a common preprocessing step in machine learning, and it is expected to be performed in any real-world application of the microTEDAclus model. However, it is important to note that the way it is performed in the original work's experiments, in which the minimum and maximum values of the features are computed over the entire dataset, constitutes a form of data leakage.

Data ordering is expected to impose the most harm on the original work's experiments validity. For this experiment, the downsampled dataset is reordered by the cluster labels, in a way that all samples from the same cluster are contiguous. \cref{fig:ordered_batches} show the scatter plot of the batches with index 0, 10, 20, and 30. \cref{fig:unordered_batches} shows the scatter plot of the same batches in the original downsampled dataset.

The third static dataset, \textbf{Cassini}, is generated in the original work by \textbf{R}'s library \texttt{mlbench} and used in its original form, without any preprocessing. Because it is originally ordered by cluster labels in the \texttt{mlbench} library, this work's experiments randomly shuffle the samples to avoid the same problem of data leakage and unrealistic batch composition.

\subsection{Concept Drift}

The \texttt{streamMOA} concept drift datasets used in the original work are \textbf{STR-B1}, \textbf{STR-B2}, and \textbf{RBF}. The scatter plots shown in the original work suggest that the noise samples of those datasets, labeled by the library as \texttt{NA}, are removed from the evaluation. Because of the reasons previously discussed, this reassessment includes the noise samples in the evaluation, as they are part of the dataset and can have a significant impact on the results. To prevent parsing issues, the noise samples are relabeled as \texttt{-1} once each dataset is loaded.

\subsection{Scalability}

For the scalability experiments, in which memory and execution time are profiled for increasing numbers of samples or feature dimensions, the original work uses synthetic datasets generated by the \texttt{streamMOA} library. The generation process and conditions are well described in the original work, and shows that the synthetic datasets lack the introduction of noise. To ensure that the scalability experiments reflect real-world scenarios, this reassessment generates synthetic datasets with noise.
